Temporal Event Dispatcher

Two ways to move payment events from Postgres into Temporal without overloading Temporal's Aurora database. We build both, measure both and pick one.

KotlinKotlin FlowQuarkusPostgresExposedTemporal on Aurora PostgresOracle (later)

It's 9:02 on a Monday morning. The overnight wire and ACH files have just been processed, and 5,000 inbound payments are sitting in the payment_events table. Somewhere, a customer is refreshing a banking app to see whether the rent money has arrived. Behind Temporal sits one Aurora Postgres cluster, and it also stores the history of every other workflow the bank runs.

The first design that comes to mind is a loop: read the new rows and start a workflow for each one. Most of us would write it first, because it works beautifully in a demo with ten rows. The trouble only shows up at 9:02 on a Monday, with real volume and a shared database.

We've already settled two things. The table is the source of truth, and a Temporal Schedule per event type is what wakes a dispatcher up. The open question is what the dispatcher does once it's awake. Does it run a plain loop, or a pipeline built with Kotlin Flow, Kotlin's own take on reactive streams?

In this page, we'll build the dispatcher three times: a naive version, a careful loop and a Kotlin Flow version. We'll measure the last two on a laptop with the same 5,000 payments. Then we'll weigh them, pick one, and look at a PoC you can run yourself.

The five event types in the PoC. Each one has its own schedule, task queue and workflow.

INBOUND_PAYMENTWire, ACH or RTP credit received
PAYMENT_RETURNEDACH return (R01, R02 …)
PAYMENT_SCHEDULEDPayment set for a future date

PAYMENT_SETTLEDClearing confirmed settlement

1A loop that starts everything at once

Let's begin with the version that comes to mind first, so we can see exactly where it breaks. We won't run this one; the arithmetic is enough.

NaiveDispatcher.kt
// Naive: this will not survive 9:02 on a Monday
fun dispatchEverything() {
    val rows = repo.findAllNew()                        // all 5,000 of them
    rows.forEach { row ->
        client.newUntypedWorkflowStub(row.type.workflowType, optionsFor(row))
            .start(EventRef(row.id, row.type.name))     // as fast as the loop can spin
    }
}

Read it slowly and it looks fine. Every row gets a workflow, and Temporal's workflow IDs even stop the same event from starting twice. Now picture the 9:02 burst. The loop fires 5,000 start calls as fast as it can spin. Each start writes to Temporal's history tables, and each workflow writes again for every activity it runs. Aurora receives the whole morning's work in a few seconds.

A few quieter problems hide in there too. Run two replicas of the app, and both read the same rows. Nothing records that a row was picked up, so a crash halfway through leaves us guessing which payments went out. And nothing in the loop ever says "that's enough for now".

Think of a restaurant host on a busy evening. A host who walks every waiting guest into the dining room at once doesn't make dinner faster. The kitchen falls behind, and everyone waits longer. A good host seats people only as tables free up, and at a pace the kitchen can handle. In programming terms, the host is our dispatcher, the tables are in-flight workflow slots, and the kitchen is Temporal with its Aurora database.

Start only what you can afford to have open. Put a cap on it.

So the dispatcher needs to claim rows carefully and stop at a cap. That's our first real version.

2Version 1: a schedule and a polite loop

Each event type gets its own Temporal Schedule. Every 30 seconds to 5 minutes, depending on the type, it starts a DispatcherWorkflow, and that workflow runs a single activity. This is Option 1.

Before we read any code, let's watch it run. In the picture below, payments arrive over HTTP on the left and wait in the table. Each schedule counts down to its next tick and wakes the dispatcher, which claims and starts. The business workflow on the right does the real work and marks the row done. Press Next to follow a single payment one step at a time (Prev goes back), or Play to watch live traffic. The step list above the picture shows every step, highlights the one that is happening and scrolls along with it. Then try pausing one schedule, say Inbound, and watch its payments pile up while the others keep moving.

Notice how the dots leave the dispatcher one by one, and how a payment that lands just after a tick has to wait for the next one. Inside the dispatcher box is the loop below.

PollingDispatchEngine.kt (trimmed)
// Version 1: claim only what we can afford, start one at a time
while (clock.instant().isBefore(deadline)) {
    val capacity = limits.maxInflight - store.countInflight(type)
    if (capacity <= 0) { Thread.sleep(500); continue }       // at the cap: wait, don't push

    val batch = store.claim(type, min(capacity, limits.batchSize), limits.lease)
    if (batch.isEmpty()) break                                 // table drained

    for (event in batch) {
        bucket.acquireBlocking()                               // a steady pace, no bursts
        starter.start(event)                                   // duplicate IDs are rejected
        store.markStarted(event.id, type.workflowId(event.id))
    }
}

Three lines do the heavy lifting. The capacity check is the host glancing at free tables: claimed and running rows count against maxInflight, and at the cap the loop waits instead of pushing. The claim call locks a batch with FOR UPDATE SKIP LOCKED and marks it CLAIMED with a lease. A second replica skips those rows, and if a run crashes, its rows come back when the lease expires. Finally, the token bucket spaces the starts evenly, so even a big backlog reaches Temporal as a steady stream.

Before running it, I expected two weaknesses. Nothing happens until the next tick, and the starts go out one at a time. Let's insert the 5,000 payments and see whether the numbers agree.

Correctness first: all 5,000 workflows started, none started twice, and every one finished. The timing depends on where in the minute the burst lands. In one run it landed just after a tick, and the first row was picked up 57 seconds later. In another it landed one second before a tick (we got lucky), and pickup took 1.6 seconds. Once running, the loop started 123 workflows per second and had all 5,000 started after 40.6 seconds.

You may be thinking, "Then let the schedule tick every five seconds." We could. But each tick is a workflow run with its own history in Aurora. Five event types ticking every five seconds come to 86,400 dispatcher runs a day, and nearly all of them would find an empty table. That's a curious way to protect a database. It would also still start one workflow at a time.

Two numbers bother us now: up to a minute before anyone looks, and 123 starts a second when Temporal could clearly take more. Kotlin Flow can help with both.

3Version 2: a doorbell and a Kotlin Flow

Option 2 keeps everything we just built: the schedules, the claim, the cap and the token bucket. It adds two pieces, and both are plain Kotlin Flow from kotlinx.coroutines. No other reactive library is involved.

Here is the same picture with those two pieces in place. Keep an eye on the doorbell at the bottom: when inbound or returned payments land, it rings, and their dispatcher starts within moments instead of waiting for the tick. Press "Send 20 inbound" in both diagrams and compare them. The dispatcher here starts them eight at a time. Pausing still works the same way, and the doorbell respects it.

Let's open up the two pieces, starting with the doorbell.

The doorbell

The first piece answers a simple question: how do we hear about new rows without polling for them? A small trigger on the table calls pg_notify with the event type whenever rows are inserted. The app listens on its own JDBC connection and turns the notifications into a Kotlin Flow.

Doorbell.kt (trimmed)
// Version 2, part 1: Postgres LISTEN as a cold Kotlin Flow
fun pgNotifications(url: String, user: String, password: String, channel: String): Flow<String> = flow {
    DriverManager.getConnection(url, user, password).use { conn ->
        conn.createStatement().use { it.execute("LISTEN $channel") }
        val pg = conn.unwrap(PGConnection::class.java)
        while (true) {
            currentCoroutineContext().ensureActive()
            pg.getNotifications(1_000)?.forEach { emit(it.parameter) }   // payload = event type
        }
    }
}.flowOn(Dispatchers.IO)

// One connection, shared by every event type
val rings = pgNotifications(url, user, password, "payment_events")
    .retryWhen { _, attempt -> delay(backoff(attempt)); true }      // reconnect, forever
    .mapNotNull { payload -> EventType.entries.firstOrNull { it.name == payload } }
    .shareIn(scope, SharingStarted.Eagerly)

doorbellTypes.forEach { type ->
    rings.filter { it == type }
        .conflate()                                                 // ten rings, one trip to the door
        .onEach { triggerUnlessPaused(type); delay(2.seconds) }
        .launchIn(scope)
}

The flow { } builder wraps the LISTEN loop. Each call to getNotifications(1_000) waits up to a second for news, and ensureActive() lets the app stop the loop cleanly. The flow is cold, so nothing happens until someone collects it. Then retryWhen reconnects after a dropped connection, and shareIn turns the cold flow into a hot one, so a single database connection feeds every event type.

The conflate() call is where the doorbell earns its name. If the bell rings ten times while you walk to the door, you still make one trip, because a ring only says that someone is there. In programming terms, a burst of 5,000 inserts produces a handful of rings, and each event type turns them into at most one schedule trigger every two seconds.

The trigger uses the overlap policy BUFFER_ONE: if a dispatcher is already running, Temporal queues exactly one more run behind it. And because a manual trigger may not respect a paused schedule, the doorbell checks the paused state first.

The pipeline

The second piece replaces the inner loop with a Flow pipeline. Compare it with the loop above; the shape is the same, but the waiting is different.

ReactiveDispatchEngine.kt (trimmed)
// Version 2, part 2: the dispatch run as a Flow pipeline
flow {
    while (clock.instant().isBefore(deadline)) {
        val capacity = limits.maxInflight - store.countInflight(type)
        if (capacity <= 0) { delay(500); continue }              // at the cap: wait, holding no thread
        val batch = store.claim(type, min(capacity, limits.batchSize), limits.lease)
        if (batch.isEmpty()) break
        emit(batch)                                                // suspends until the start stage has room
    }
}
    .flatMapConcat { it.asFlow() }
    .flatMapMerge(concurrency = limits.parallelism) { event ->
        flow {
            bucket.acquire()                                       // suspends instead of blocking
            emit(withContext(io) {
                starter.start(event).also { store.markStarted(event.id, type.workflowId(event.id)) }
            })
        }
    }
    .collect { outcome -> tally(outcome) }

The interesting word is emit. It suspends until the next stage is ready for more, so the pipeline claims a new batch only when the start stage has room. That's backpressure, and we didn't write a line of queue management to get it. flatMapMerge keeps up to parallelism start calls in flight (8 for inbound payments). The token bucket now suspends instead of blocking, so a waiting start holds no thread. The PoC's tests check both promises: never more than parallelism calls at once, and never more than parallelism unstarted rows when a new batch is claimed.

Same 5,000 payments, same limits. Correctness first again: 5,000 started, zero duplicates, all finished. The first row was picked up 0.4 seconds after the insert. The pipeline started 340 workflows per second and had all 5,000 started after 14.7 seconds, about 2.8 times faster than the loop. Five insert statements produced five rings and only two triggers, which is the doorbell doing its job. A later run with the default limits started 2,000 payments in 10.5 seconds, exactly what a rate limit of 200 per second allows.

You may be asking, "What if a notification gets lost?" Then a ring is lost, and nothing else. The table still holds every row, and the interval ticks keep running underneath. We even saw this happen by accident. In one run, an earlier build of the doorbell couldn't connect (it used a different Postgres client that was missing a library). Option 2 quietly behaved like Option 1, and every payment was processed.

A notification is a hint. The table is the truth.

So Kotlin Flow made dispatch 2.8 times faster. Does that mean payments finish 2.8 times faster? Let's look at the column we skipped.

4Where the speed-up stops

Look at the last row of the first run: 117 seconds for the loop, 115 for Flow. All that faster dispatching saved two seconds end to end. The second run, with the default limits and slower simulated activities, is even plainer: both options settled at about 85 starts per second.

Back to the restaurant. A faster host fills empty tables sooner, but once every table is taken, new guests wait for someone to leave. The seating rate then equals the number of tables divided by how long each meal lasts. That's Little's law. In the second run the cap was 2,000 open workflows and each stayed open for about 24 seconds (the workers were busy), so neither option could seat more than about 83 a second. The host was never the bottleneck; the kitchen was.

This is the honest limit of reactive streams here. Flow's backpressure reacts to one thing: how long a start call takes. When Temporal slows down, the eight slots stay busy and claiming slows by itself, which is exactly what we want. But Flow can't see how many workflows are open, or how hot Aurora's CPU is running. The in-flight cap sees the first. A future load governor will watch the second.

Flow's backpressure protects the dispatcher. The in-flight cap protects Aurora.

5Weighing the two options

Here is everything we've learned so far, laid side by side.

Option 1

Schedules with a plain loop

Simpler
Schedule tick (30s–5m)→DispatcherWorkflow→claim ≤ capacity→start one at a time→mark STARTED

Pros

  • Fewest moving parts: a schedule, one activity and a status table.
  • A plain loop that's easy to read, test and debug.
  • Backpressure by design: it pulls only what capacity allows, one start at a time.
  • Works the same on Postgres and Oracle.

Cons

  • Pickup waits up to one interval (57 s in our run).
  • Sequential starts: 123 per second in our run.
  • A burst waits for the next tick even when Temporal is idle.
Option 2

Schedules with Kotlin Flow

Recommended
INSERT → pg_notify→LISTEN as a Flow→conflate()→schedule.trigger()→claim → flatMapMerge(8) start

Pros

  • Pickup in under a second for types with the doorbell on (0.4 s in our run).
  • Bounded parallel starts: 340 per second in our run, still capped by the rate limit.
  • Demand-driven claiming, built into Flow: the next batch waits for room.
  • Slows down by itself when Temporal's response time rises.
  • If the listener stops, interval ticks drain the table exactly as in Option 1.

Cons

  • More code to own: a LISTEN connection, reconnects, conflation and coroutines inside a blocking activity.
  • Push works only on Postgres. Oracle sources get the Flow pipeline but no doorbell.
  • Manual triggers need their own pause check.
  • Concurrency is harder to test and to reason about.
  • NOTIFY takes a lock at commit, so keep the doorbell off for very busy event types.

Lists like these hide how much each point matters to you, so the scorecard below lets you set the weights yourself. The defaults lean on what this design must do well: latency, throughput, pause and resume, and staying easy to maintain.

With the default weights the two options land within a point of each other, and I'd be suspicious of any comparison that pretended otherwise. The points that differ, though, are the ones payments feel: how long an inbound credit waits, and how quickly a month-end burst clears.

You may be thinking, "If they score the same, pick the simpler one." That's a sound instinct, and often the right call. Here, though, Option 2 contains Option 1: switch its doorbell off and it behaves exactly like the loop. So the real question is asked per event type: is the faster pickup worth a listener? For inbound payments and returns, I think it is. For settlements that arrive in clearing batches, it isn't.

So the recommendation is Option 2, Temporal Schedules with Kotlin Flow, with the doorbell on for INBOUND_PAYMENT and PAYMENT_RETURNED and off for the rest. Option 1 is still the better choice when:

  • every event type's latency target is at least its schedule interval,
  • peak volume per type stays under roughly 1 ÷ start latency (about 120 per second in our run),
  • the team wants the smallest surface to own and isn't comfortable with coroutines yet, or
  • the source is Oracle only, so the doorbell can't be used.

Reading about it only goes so far. Let's run it.

6Run it on your laptop

What's in the repo

  • A Quarkus and Kotlin app with Exposed on Postgres, Flyway migrations and the Temporal Java SDK.
  • One generic DispatcherWorkflow and one Temporal Schedule per event type.
  • Two dispatch engines, PollingDispatchEngine and ReactiveDispatchEngine, chosen with DISPATCH_MODE.
  • Doorbell: JDBC LISTEN as a cold Kotlin Flow, shared with shareIn and conflated per type.
  • An ingestion API, POST /events/{type}, that validates the payload and stores it as NEW.
  • Five business workflows with realistic payloads, plus a sample-data generator.
  • An admin API for stats, pause and resume, and live limits.
  • 30 tests, including real Postgres through Quarkus Dev Services.

Back to Monday morning

We started with a loop that started everything at once, like a host sending every guest into the kitchen together. A cap and a lease turned it into a polite loop. Kotlin Flow then gave us a doorbell and parallel starts: 2.8 times faster to start a burst, and a useful reminder that faster seating doesn't cook the meals any quicker.

Before you close this page, search your own code for a call to WorkflowClient.start inside a loop over query results. If there's no cap and no SKIP LOCKED nearby, you may have just found next Monday's incident.

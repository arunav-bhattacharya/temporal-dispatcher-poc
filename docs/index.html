Design comparison · payment events → Temporal

Temporal Event Dispatcher

Two ways to turn payment events stored in Postgres into Temporal workflows without overloading Temporal's Aurora database. Both use one Temporal Schedule per event type. The difference is whether reactive streams (Postgres NOTIFY plus Kotlin Flow) sit in front of and inside the dispatcher.

Recommendation

Option 2: Schedules with reactive streams, switched on per event type

It's a close call on paper. Option 2 wins on the two things payments feel most, latency and burst throughput. Its extra parts can be switched on per event type, and when they fail it falls back to Option 1's behavior.

  • Pickup in seconds for inbound and returned payments
  • Bounded parallel starts that slow down automatically when Temporal slows
  • Same controls as Option 1: pause, overlap policy, rate limits, governor
  • Cost: a listener and a coroutine pipeline to build, test and run
  • The PoC runs both: DISPATCH_MODE=polling or reactive

1The two options

Same table, same schedules, same workflows. Option 2 adds a wake-up signal and runs the dispatch loop as a Flow pipeline.

Option 1

Schedules without reactive streams

Simpler
Schedule tick (30s–5m)→DispatcherWorkflow→claim ≤ capacity→start one at a time→mark STARTED

Pros

  • Fewest moving parts: a schedule, one activity and a status table.
  • A plain loop that's easy to read, test and debug.
  • Backpressure by design: it pulls only what capacity allows, one start at a time.
  • Works the same on Postgres and Oracle.

Cons

  • Pickup waits up to one interval.
  • Sequential starts cap throughput at 1 ÷ start latency per event type (about 50/s at 20 ms).
  • A burst waits for the next tick even when Temporal is idle.
Option 2

Schedules with reactive streams

Recommended
INSERT → pg_notify→Flow: latest ring, 2s gap→schedule.trigger()→DispatcherWorkflow→claim → flatMapMerge(8) start

Pros

  • Pickup in seconds for event types with the doorbell on.
  • Bounded parallel starts: up to n ÷ start latency, still capped by the rate limit.
  • Demand-driven: the next batch is claimed only when the start stage has room.
  • Slows down by itself when Temporal's response time rises.
  • If the listener dies, interval ticks still drain the table, exactly as in Option 1.

Cons

  • More code: a LISTEN connection, reconnects, debouncing and a coroutine pipeline inside a blocking activity.
  • Push works only on Postgres. Oracle sources get the Flow pipeline but no doorbell.
  • Manual triggers need their own pause check.
  • Concurrency is harder to test and reason about.
  • NOTIFY takes a lock at commit, so keep the doorbell off for very busy event types.

2Backpressure

Where each option limits the flow of work, from new rows in the table to open workflows in Temporal.

StageOption 1 · without reactiveOption 2 · with reactive
New-event signalTimer only, so there is nothing to overflow.NOTIFY pushes without backpressure. Each type's ring flow keeps only the latest ring (buffer 1, drop oldest) and triggers at most once every 2s. Dropping extra rings loses nothing, because a ring only means "look at the table".
Claiming rowsEach batch claims at most maxInflight − in-flight rows.Same query. The Flow claims the next batch only when downstream asks for it, because emit suspends until then.
Starting workflowsOne call at a time: throughput ≤ 1 ÷ latency.flatMapMerge(n) keeps up to n calls in flight: throughput ≤ n ÷ latency.
Rate limitToken bucket that blocks the thread.Token bucket that suspends, so no thread is held while waiting.
Temporal slows downEach call takes longer, so the loop slows on its own.All n slots stay busy, demand drops and claiming slows on its own, with n times the headroom.
MemoryOne batch.n calls in flight plus a small bounded buffer.
Open workflows and Aurora loadIn-flight cap plus the future governor.Same in-flight cap and governor. Reactive backpressure doesn't reach this far.

Reactive backpressure works between stages inside one process. It reacts to how long each start call takes. It can't see how many workflows are open in Temporal or how busy Aurora is. In both options, that's the job of the in-flight cap and, later, the governor.

Run A: in-flight cap 20,000, rate limit 1,000/s, no simulated activity delay. Run B: default limits (in-flight cap 2,000, 200/s) with 10 ms per simulated activity.

  • Parallel starts pay off only when the start call is the bottleneck. In Run A they started the burst 2.8× faster.
  • Neither option makes Temporal run workflows faster. When the workers set the pace (Run B), both settle at the in-flight cap's rate, as Little's law predicts: about 80 starts/s for 2,000 open workflows that each take about 25 s. End-to-end drain time was set by the workers in both runs.
  • The doorbell held up. 5 insert statements produced 5 rings and 2 triggers. With PAYMENT_RETURNED paused, its 200 rows stayed NEW and the doorbell skipped the ring. After resume, all 201 completed within 10 s.
  • Run B also showed the fallback working. With the listener down, Option 2 behaved like Option 1 and nothing was lost.

6Decision

Why Option 2

  • Latency where it matters: inbound credits and returns get picked up in seconds. Future-dated and settled events don't need it, so their doorbell stays off.
  • Bursts: month-end or a clearing file can land thousands of rows at once. Parallel starts with a cap drain them in seconds instead of minutes.
  • Self-limiting: when Temporal slows, the pipeline slows with it. It never has more than n calls in flight per dispatcher.
  • No new failure mode for correctness: the table stays the source of truth. A lost ring costs at most one interval of delay.
  • Same ops model: the same schedules, pause/resume, dispatch_config limits and governor.

Choose Option 1 instead if

  • Every event type's latency target is at least its schedule interval.
  • Peak volume per type stays under about 1 ÷ start latency (roughly 50/s).
  • The team wants the smallest surface to own and isn't comfortable with coroutines yet.
  • The source is Oracle only, so the doorbell can't be used.

Both run from one codebase, so you can start with Option 1 and turn on reactive per event type later.

7Run the PoC

What's in the repo

  • Quarkus + Kotlin app with Exposed on Postgres, Flyway migrations and the Temporal Java SDK.
  • One generic DispatcherWorkflow and one Temporal Schedule per event type.
  • Two dispatch engines: PollingDispatchEngine and ReactiveDispatchEngine.
  • Doorbell: Vert.x PgSubscriber → Kotlin Flow → schedule.trigger().
  • Five business workflows with realistic payloads and a sample-data generator.
  • Admin API: stats, pause/resume, live limits.
  • Docker Compose: events Postgres, a second Postgres standing in for Temporal's Aurora, Temporal and its UI.

Run it

terminal
# infra: Postgres ×2, Temporal, Temporal UI (localhost:8233)
docker compose up -d

# option 1 (default) or option 2
./gradlew quarkusDev
DISPATCH_MODE=reactive ./gradlew quarkusDev

# insert a burst and time it (first pickup / all started / all finished)
python3 scripts/watch_stats.py --generate INBOUND_PAYMENT:5000

# ops levers
curl localhost:8080/admin/stats
curl -X POST 'localhost:8080/admin/schedules/INBOUND_PAYMENT/pause?note=incident'
